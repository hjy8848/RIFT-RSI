Scope: runtime data and trust boundaries for dual-bank learning

This document describes how the dual-bank learning objective flows through the existing Usami and VERL adapters. The research decision is in [RESEARCH_SPEC.md](RESEARCH_SPEC.md); versioned bank and reward rules are in [DUAL_BANK_DESIGN.md](DUAL_BANK_DESIGN.md).

## Runtime boundaries

Usami native worlds, Customer/Engine/Tool sessions, task certificates, replay records, final business outcomes, and private evidence remain inside the Host. The Service receives real multi-turn observations and tool results. It does not receive Oracle fields, strict process labels, hidden task identities, or probe membership. A public tool failure is a normal observation, not an Oracle annotation. The trusted evaluator may award only replay-verified `business_goal_success`; `strict_task_success` is not the learning reward.

`FailureObservation` is the Designer's allowlisted input: an opaque TaskRef plus its public summary. `TaskEvidenceRecord` stays Host-private and uses the common `BANK_CANDIDATE` purpose for both failure and success observations. UNKNOWN remains explicit and never becomes a negative label.

`AbilityRegistry` is a durable Host-owned index of capability-gap hypotheses, not a source of hidden benchmark labels. One captured Designer decision returns an existing ability ID or `NEW`, its hypothesis and visible failure TaskRefs, one native `ScenarioDraft`, and multiple native `AbstractChallenge` records. The Host binds the complete plan to the captured on-policy generation, validates IDs and public references, allocates a stable ID for `NEW`, and records explicit association edits only. No semantic matching is performed.

`CommerceHost.certify_training_plan()` compiles and builds one frozen Usami World, verifies the native build, then grounds, compiles, and certifies each challenge against that World. It tries native Grounding candidates in their deterministic budgeted order; only certified TRAIN tasks are registered for execution. Per-challenge `NO_MATCH`, `UNSAT`, and `UNKNOWN` evidence remains in the result. `TrainingPackage` freezes selected Designer TaskRefs, a reproducibly sampled set from a pre-certified Benchmark TRAIN pool, source identities, one same-task GRPO group per TaskRef, the seed and mix configuration, World/build evidence, and the Service checkpoint. Default configuration budgets 16 tasks at 8 Designer and 8 Benchmark tasks. The native runner clones the frozen World for each episode.

`prepare_package_service_update()` reuses the existing replay-verified token-capture and Service trajectory path. It checks every package TaskRef against `CertifiedTaskRegistry`, requires complete same-task groups, and records realized rollouts, tokens, and unmasked optimization tokens by source. UNKNOWN outcomes discard their whole GRPO group. The realized groups must retain the configured source ratio; otherwise package preparation fails instead of silently changing the mix. `LoopState` schema 4 records the one-to-many package binding and realized statistics, while schema 1–3 states keep the legacy one-proposal/one-task protocol. Package identities are checked against both frozen dual-bank snapshots under their split policy. The delayed dual-bank scalar remains one reward for the original Designer action.

## Banks, splits, and probes

`BankManager` persists checkpoint-relative records and membership events. Bootstrap failures enter `FailureBank` without ability labels; unlinked failures remain available across rounds. Recovery reads from this same bank. `SuccessBank` supplies Retention candidates and the legacy Replay LogP baseline. These are candidate stores, not the reward itself.

`SplitRegistry` keeps the legacy strict family-disjoint policy and adds explicit `instance_disjoint_within_family_v1`. Old JSON registries load as strict. Every Probe snapshot records its policy version, seed, protocol, task identities, baseline checkpoint, and content hash. Recovery first samples eligible failures linked to the selected ability, then randomly fills from other eligible failures. Designer-seen history is allowed. A current Service training task and substantive overlap are excluded. Each selected historical TaskRef needs a separately verified baseline under the current Service checkpoint and protocol; old scores are never reused as the new baseline. Retention remains an independent random sample. TEST tasks are rejected from banks, training, and reward scoring.

`ProbeRunner` reuses the verified baseline trials in the frozen snapshot and executes the same task and seeds after the update. `score_dual_bank` requires complete Checkpoint, split, protocol, seed, trial and trusted Episode evidence bindings. It rejects scripted evidence and returns no scalar when valid coverage is insufficient. Its task-equal reward is `Recovery gain - λ * max(0, Retention regression)`. Independent TEST output is researcher-only and is not passed into bank update or Designer feedback.

## Policy updates and credit

The Service remains a full-parameter VERL 0.9.1 FSDP2 policy with vLLM rollouts and GRPO. `UsamiServiceAgentLoop` drives each episode through the native Host session and records actual token IDs and response masks. A complete same-prompt group is required; UNKNOWN or failed evidence invalidates the whole group.

Designer generates one package-level World-and-challenges plan from FailureObservation and available ability IDs, with the generating policy/checkpoint/action stored. After Usami certification, Service training and dual-bank post-update evaluation, the verified scalar is assigned once to that captured Designer rollout. Sequential rewards across changing Service checkpoints do not form comparable GRPO groups. The dual-bank Designer backend uses full-parameter `reinforce_baseline` with an explicit scalar baseline, no fabricated group ID and no batch whitening. The prior Replay LogP path remains independently selectable as an experimental baseline.

`LoopState` stores and validates the protocol tag and each transition. Old state JSON without a reward tag is loaded as Replay LogP; it is never reinterpreted as a dual-bank reward. Each external operation is followed by a durable state save, and resume requires the runtime's trusted update, reward, action, snapshot, and trial verifiers.

`EvolutionScheduler` coordinates bootstrap, explicit ability selection, round plan validation, frozen Probe preparation, both policy updates, delayed Designer credit, ability history, bank refresh and optional isolated TEST callbacks. A round plan binds the selected package plan to the original Designer output, current visible context, all package identities, and the Service request. `rift-evolve` invokes it through an application-owned `EvolutionRunRuntime` factory. That factory must supply production Usami stores, VERL worker groups, evidence verifiers, checkpoint store, plan factory and bank updater. Importing code starts no model or training job; mocks are not accepted as real evidence.

`CommerceHost` and the worker-side `NativeHostProvider` can share one `CertifiedTaskRegistry` for resolving and authorizing a certified task. `SplitRegistry` remains the separate source for cross-split identity checks; CommerceHost no longer keeps a second task-object cache. Native Grounding returns a deterministic, budget-capped candidate sequence, which the host tries until certification succeeds. The default Customer profile handles mixed and information-only task shapes, but Usami's current proof certifier still marks information objectives UNKNOWN without an interaction certifier.

## Current deployment boundary

The repository pins VERL v0.9.1 commit `1876b06d0a3e4e71e06230be10af14492ca8a75b` and retains the requested 8×Ascend 910B3 configuration. CPU tests run native Usami World construction, Grounding, certification, episode execution/replay, frozen Benchmark sampling and package state recovery. Mock capture and verifier tests cover the VERL request boundary only; they do not demonstrate a model update. The real Ray/FSDP2 worker launcher, durable certified-task and Episode stores, deployment trust roots, and exclusive NPU handoff remain application-owned. The requested NumPy 1.26.4 also conflicts with upstream VERL's `numpy>=2.0.0` requirement; the target stack is not verified. See [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md).
