Status: active design
Owner: RIFT-RSI maintainers
Last verified: 2026-10-29
Scope: first-stage execution boundaries and remaining adapters

This design defines the trusted Host boundary and the stopping condition for the first implementation; see [research spec](RESEARCH_SPEC.md) and `src/rift/` for the source of truth.

Native Usami records, task objects, certificates, replay and outcome evaluation belong in the Host. `benchmark/usami.py` lazily calls the pinned native commerce APIs; `private_evaluation.py` projects allowlisted event fields and a business-only outcome. Certification reports bounded task reachability, not natural interaction solvability. A proposal and a certificate are separate objects. No raw certificate or native record is a model input. `ReplayBank` accepts replay-partition real-model successes and freezes a content-hashed snapshot only against disjoint train identities; it does not infer optimal actions. SplitRegistry rejects registered cross-split identity overlap; correct identities and lineage must still come from a trusted upstream source. Grounding and compilation call the native Usami structured challenge APIs inside the Host; the native compiler renders its request rather than trusting a free-form proposal request. The event projection is an observation summary, not a reconstruction of exact model prompts or token IDs. Capturing and validating exact model inputs, action tokens, and model interface is still required before training or genuine replay scoring.

`training/service_data.py` constructs a request only from native replay-verified episodes and a trusted future token recorder. Designer credit belongs to the entire package action, not to an individually proven task. Multiple package feedback records may be accumulated into one Designer request when they share the complete Service baseline, replay content and normalization. GRPO groups require distinct recorded Designer rollouts from the same prompt; other policy-gradient algorithms do not assume groups. `training/contracts.py` declares Service and Designer backends, checkpoint store, token-level scorer, update verifier and Designer action verifier; `replay/reward.py` computes masked before/after scores and declares a reward verifier. The verification interfaces are trust boundaries: a checkpoint's existence alone does not prove that an update produced it, a rollout ID does not prove which policy generated it, and a syntactically valid reward does not prove scoring took place. The v0.9.1 worker adapters under `rift/verl` are incomplete and have not been validated on the target runtime; see [VERL_INTEGRATION_DESIGN.md](VERL_INTEGRATION_DESIGN.md) and [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md). `loop.py` persists requests, externally reported completed updates, replay results and each Designer batch member; it requires supplied trusted verifiers again when resuming completed stages and invokes no trainer, scorer or model itself. A next-round state carries and verifies both previous completed updates, and requires the next Service and Designer requests to start from their respective resulting checkpoints.

`CommerceHost` binds every certified training task and world to the same `SplitRegistry` used for Designer experience and Replay. It requires an upstream identity factory for family and source lineage; that factory and the completeness of the registry remain trusted inputs. A registered identifier alone is not proof of its origin. Replay demonstrations retain their full source checkpoint identity, and scoring rejects a different Service policy or tokenizer. The bank, snapshot loading and reward scorer require a trusted source verifier: the `real_model` and `replay_verified` fields by themselves do not prove provenance. `NativeReplayEvidenceVerifier` can reconstruct a sample from a replayed native episode, but depends on a trusted resolver and decision verifier; production still needs an evidence store and verified token recorder.

A package cannot enter Service training unless each distinct certified task has at least one usable rollout. In particular, an UNKNOWN-only task does not silently disappear while its original package receives learning credit.

`PublicSummary` is a human-readable, non-privileged projection for the Designer; it is not an exact Service prompt. `ExactPolicyTrace` separately records token IDs, action mask, policy identity, request/response digests, serialization version and provenance. The recorded-trace adapters bind these fields to stored Service or Designer calls and require an injected generation-time attestor. Usami `AgentCall` does not contain generated token IDs, so digest matching alone does not prove that those IDs were actually used. A real inference backend, trusted capture and attestor remain necessary.

The current split policy treats family, world, task and lineage as hard cross-split disjointness keys. Family must therefore denote the intended generalization unit, not an automatically assumed broad label such as “refund”. This conservative default can make replay scarce. Same-family, disjoint-instance transfer is a distinct experimental condition and is not supported by the current registry; it requires an explicitly versioned split policy rather than silently weakening existing checks.
