## Service loop and reward

A custom `AgentLoopBase.run` is registered by `actor_rollout_ref.rollout.agent.agent_loop_config_path`. Its host owns a certified task, native customer session and Usami Engine; only public messages and genuine tool outputs reach Service. The implementation must drive the interactive native state machine step by step; the existing synchronous `run_episode` owns the entire episode and cannot simply be called for each asynchronous generation. Preserve tool errors as observations and do not score them as privileged process labels. Model-side malformed tool calls become native Service protocol failures and remain scored as business failures when replay verifies. A parser/runtime exception instead follows Usami's cancellation path, preserving the Episode and generated tokens with UNKNOWN business reward. After a native episode is complete and native replay verifies, emit only `business_goal_success` as 1/0. UNKNOWN, failed replay, incomplete capture and certification failure must cause exclusion before grouping/update, not conversion to zero. A custom Reward Loop can consume an opaque, host-verified outcome reference, or a verified `AgentLoopOutput.reward_score` can be populated by the host; no private native record or Oracle fields enter reward metadata.

## Exact tokens and grouping

The official `AgentLoopOutput` contains `prompt_ids`, `response_ids`, `response_mask`, optional `response_logprobs` and metadata. The official tool loop uses the Continuous Token builder and appends tokens returned by the model server, masking tool/user tokens to zero. Capture the actual server-generated token IDs and exact per-decision input prefix *before* generation, not a post-hoc re-tokenization of reconstructed messages. Store model checkpoint identity, tokenizer and chat-template versions, per-turn boundaries, role mask, rollout ID, task/package ID, and group ID. Ensure actual action-token identity matches the response; if serving output lacks necessary token IDs or exact continuous prefix, fail closed. The existing `ExactPolicyTrace` needs generation-time evidence plus per-turn boundaries; event-projected `PublicSummary` is not a policy input or scorer context. Non-action tool tokens are visible context for subsequent decisions and are excluded by the loss mask.

Service uses on-policy GRPO only for multiple independent complete rollouts of the *same exact initial prompt and task*, sampled under the same checkpoint and frozen generation settings. Group IDs and expected group size must be assigned before sampling; per-rollout seeds are derived from the rollout identity and checked for uniqueness. For paired Probe evaluation, the CustomerFactory receives the frozen task seed and Service per-turn seeds use a task/seed/protocol scope that stays fixed across checkpoints; the checkpoint-bound rollout identity remains distinct. Exact Service sampling settings are retained in generation evidence. The evidence verifier checks the exact first prompt, task identity, common settings, distinct seeds, and that every planned group member arrived. Multi-turn responses preserve the environment tokens and mask. If a member has UNKNOWN outcome, the entire group is discarded; it is never converted to zero or trained as a smaller group. A variable number of verified groups may be insufficient for the configured global mini-batch; stop instead of changing the group semantics. Existing per-decision `Rollout` is not automatically a valid GRPO sequence and must be replaced by the faithful whole-episode token stream.

## Checkpoints and Replay

Before a package update, freeze a verified full Service checkpoint, including FSDP2 model shards and the metadata needed for resume. Checkpoint revisions are numeric VERL global steps. One RIFT package invokes one outer `update_actor` batch; VERL may run multiple minibatches and epochs internally, but increments its outer global step once. The adapter therefore saves at `before_step + 1` and rejects a mismatched revision. After successful optimization and checkpoint save, independently resolve and hash the complete after checkpoint; distinct filenames are insufficient. `VerlCheckpointWeightSync` calls the official v0.9.1 `CheckpointEngineManager.update_weights(global_steps=...)` on the same actor worker group. `VerlServingAttestor` records completion and checks every vLLM `TokenOutput`'s `global_steps`, `min_global_steps`, and `max_global_steps` against that checkpoint step; trajectories that cross a revision are rejected. Upstream exposes a step marker rather than a tensor hash from the inference replica, so this is a step-bound acknowledgement, not a cryptographic proof of server memory. Failed or partial saves/weight sync cannot produce `TRAINING_COMPLETED`. An interrupted update must resume from the last complete checkpoint with recorded phase and RNG/optimizer state, or restart a package from its original before checkpoint; never count an unverified update.

Replay scorer loads the two full Service checkpoints in sequence and invokes actor `compute_log_prob` on identical token sequences and masks. In v0.9.1 the actor worker consumes TensorDict; trainer padding utilities convert left-padded prompt/right-padded response into no-padding input and slice next-token log probabilities. Preserve zero-mask environment tokens in the context. Record tokenizer/template identity, exact snapshot digest, per-sample before/after scores and normalization. The score is a proxy, not task success. Device memory and single-node rank layout must be handled by the same FSDP2 lifecycle, without implicitly loading two models simultaneously.

## Designer and scheduling

Designer receives opaque Failure Bank references with public summaries and the available explicit ability IDs. Its on-policy structured action selects an existing ID or `NEW`, gives a hypothesis, diagnosis task references and a task proposal, and is stored with exact generated tokens. Host checks the selected choice against the captured output and visible request context; `NEW` receives a stable Host ID. The Designer checkpoint, rollout and generation settings remain bound before Service updates. The delayed reward is the verified dual-bank business outcome: Recovery task-success gain minus `λ` times Retention regression. It requires real, frozen independent probes, identical task/seed/protocol before and after, and verified full Service checkpoints. Difficulty, certification, strict process success, and generated-task outcome are not Designer reward. The legacy Replay LogP mean remains a separate experimental baseline.

Sequential dual-bank rewards follow different Service checkpoints and are not comparable GRPO samples. The Designer adapter therefore uses ungrouped `reinforce_baseline` with a configured scalar baseline and without batch whitening. It retains the original on-policy action until the corresponding Service update and Probe evaluation complete. GRPO is only allowed for a genuine matched-baseline design with independent proposals sharing the same policy start, Service before checkpoint, frozen probes, protocol and update budget; this version does not synthesize those groups. Do not duplicate samples to satisfy GRPO.

The coordinator owns two independently checkpointed trainers and alternates exclusive ownership of the 8 NPUs: Designer rollout, Service update, before/after independent Probe evaluation, delayed Designer update. Persist boundaries before external operations, version every policy and snapshot, release/restore FSDP2 and vLLM resources between phases, and resume idempotently. Checkpoint success, weight-sync acknowledgement, evidence records and update IDs are required for transitions. No training method may be invoked by importing modules. No implementation may fabricate a checkpoint or update when the actual backend is absent.

## Reuse and required changes

Reuse Usami certification/business-outcome projection, ReplayBank and its old reward arithmetic, checkpoint identity and split registry. The current adapter adds an interactive native session, exact continuous-token capture, an Agent Loop, whole-episode Service GRPO data, separate Designer pending rollouts, full checkpoint-file hashing, a VERL worker-group scorer/backend, step-bound weight-sync receipts, and a resumable round coordinator. CommerceHost and NativeHostProvider can share a CertifiedTaskRegistry; SplitRegistry remains responsible for partition conflicts. `rift-verl-round --runtime-factory package.module:create_runtime --state path/to/round.json` remains the legacy single-round Replay LogP entry. `rift-evolve --runtime-factory package.module:create_runtime` is the dual-bank multi-round entry; its factory must return an `EvolutionRunRuntime` built from trusted Usami stores, actual VERL worker groups, bank updater, evidence verifiers and Designer plan factory. Importing either CLI starts no workers. Remaining deployment work is to supply that application-owned factory, persistent certified-task and Episode stores, a seed-aware CustomerFactory and Probe evaluator, initialize/checkpoint the VERL worker groups, manage the 8-NPU role handoff, restore pending on-policy actions across interruptions, and validate the exact Ascend software stack. CPU mocks establish interface behavior only. The requested NumPy 1.26.4 conflicts with upstream v0.9.1's `numpy>=2.0.0`; the target package combination remains unresolved. This document specifies the implemented adapter and its unverified deployment boundary; it does not claim that the end-to-end system is ready for real training.
