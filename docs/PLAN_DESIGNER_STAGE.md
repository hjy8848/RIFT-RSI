# 接入 Designer 前需要的修改

日期：2026-11-03（韩国时间）
状态：讨论稿，尚未开始改代码。

本文列出在让 Designer（出题模型）参与训练之前，我认为需要修改的全部地方。每一项都写明：改什么、为什么（依据哪次实验的哪个数据）、改在哪里、怎么验证、有什么风险。

---

## 0. 依据：这几天实验得到的事实

| 实验 | 关键数据 | 对 Designer 的含义 |
| --- | --- | --- |
| X1 筛选（Qwen3-4B，22 种题） | 17 种题成功率 ≥ 0.88；F2 默认题 0/16，原因是请求没写数量 | 现有题大部分已饱和；题目本身可能有“看不出答案”的缺陷 |
| 两轮训练冒烟 | 出题方的多任务世界：客服 0/16 | 多任务世界当前无法学习 |
| X2（均衡训练 30 轮） | F9：0.16 → 0.85；F1 干扰订单：0.09 → 0.09；保持类不掉 | 强化学习能放大“偶尔已会”的行为；学不会“从未出现过”的行为 |
| X5（随机 对 老虎机，各 1 个种子） | 老虎机：F9 两类接近满分，**F6 拒绝版 0.16 → 0.03**（每个任务都下降）；随机：F6 0.16 → 0.93；总成绩 0.71 对 0.73 | 只追学习信号会过度集中，并造成负迁移 |
| X5 选题记录 | 老虎机避开“无用题”（3 轮 对 12 轮），但学习信号 < 0.1 的轮数和随机几乎一样（14 对 15）；过早放弃 F6，过久停留在已练会的 F9 延迟版 | 学习信号是有用的选题依据，但光有它不够 |
| F1 干扰订单的动作分析 | 所有模型都只打开一张订单就开始退款；偶尔的成功来自“恰好打开了目标订单” | 需要“由易到难”的台阶题，这正是 Designer 最该做的事 |

---

## 1. 已确认的决定

1. Designer 使用 **Qwen3-4B，与客服各一份权重**。
2. Designer **能看到训练集失败任务的隐藏目标**；留出集、验证用的题**完全保密**。
3. **先修好多任务世界再用**（Designer 一个世界可以出多个任务）。
4. **不加过程奖励**：奖励只看业务结果；坏的过程应该通过环境里的后果体现，而不是写进奖励。
5. **Designer 输出完整世界草稿**（商品、订单、库存、仓库和挑战都由 Designer 写），而不是只选题型和参数。（2026-11-03 确认）

---

## 2. 第一批：必须先改

不改这些，Designer 要么训练不起来，要么得出的结论不可信。

### 2.1 多任务世界：让同一个世界里的实例可以区分

- **改什么**：多任务世界给每个实例加的区分标签，从 `variant_0 / variant_1 …` 改成显眼且互不重复的词（例如颜色）。**属性名仍然叫 `instance`**。
- **为什么**：
  - 冒烟里多任务世界客服 0/16。原因是：4 个实例的型号完全相同（`target_0_variant_2000`），唯一的区分词是 `variant 2`，又和型号里的 `variant 2000` 用了同一个词。渲染出的请求是 “damaged variant 2 target 0 variant 2000 product 0 item”。
  - 两个失败样本里，请求分别是 variant 2 和 variant 0，模型退款的都是**同一行**，说明它把型号吻合当成了找到目标。
- **为什么属性名不改**：近似题过滤（`src/rift/probes/fingerprint.py:43`）比较两道题是否只是换皮时，会**忽略 `instance` 属性**。如果改成 `color` 等别的名字，过滤就会把“只换了颜色”的题当成新题，Designer 可以借此刷分。
- **改在哪里**：`src/rift/benchmark/families.py` 的 `_expand_instances`（第 105 行起）。
- **影响范围**：只影响一个世界里有多个任务的情况。X2、X5 用的都是单任务世界，结果不受影响。
- **怎么验证**：单元测试检查同一世界内各实例的请求描述互不包含；有 NPU 后重跑一次冒烟规模的多任务世界，看客服成功率是否明显高于 0/16。
- **风险**：区分词依然是模板化语言，只解决“分不清”，不解决“语言机械”（见第 4 节）。

### 2.2 可识别性检查（计划书 C4 的一部分）

- **改什么**：出题认证时检查，客户的请求是否能**只凭公开信息唯一确定**：
  1. 目标是哪一条订单行（该客户的其他商品行的公开描述不能覆盖目标行的描述）；
  2. 要处理几件（订单行有多件、只处理一部分时，请求必须写明数量，已在 `4d9844a` 修好）。
  不满足的挑战**不通过认证**，并在结果里写明原因。
- **为什么**：
  - F2 默认题（买 3 退 1）请求里没写数量，16/16 全错，是题的缺陷，不是模型的问题。这是我人工读样本才发现的。
  - Designer 自动出题时，这类“看不出答案”的题会混进训练，而且它们的成功是随机的，学习信号还会很高，**Designer 会被奖励去出这种题**。
- **为什么选择拒绝而不是自动修补**：拒绝并给出原因，Designer 能从失败里学到“要写清楚”；自动修补则让它学不到。
- **改在哪里**：Usami 的出题认证环节（落地与认证代码，`third_party/usami/usami_v2/scenarios/`），描述规则复用 `tasks.py` 里的 `_line_description`。
- **范围限制**：只查“哪一行、几件”。其他歧义（比如允许多种补救方式时客户想要哪种）先不查。
- **怎么验证**：构造“两行描述相同”“缺数量”的反例，确认不通过；全部现有题型在 CPU 上重新认证，确认没有误杀。
- **风险**：可能有一部分现有题不再通过认证。需要逐个看被拒的原因，确认是真有歧义，而不是规则写得太严。

### 2.3 Designer 认识新题型（计划书 C15）

- **改什么**：Designer 的提示词和输出格式，覆盖现在 Usami 支持的全部目标类型：退款数量、换货（含指定属性、加价上限、到货期限）、取消订单、实物退回（含收货延迟）、拒绝（正确做法是不执行）。
- **为什么**：现在的 Designer 路径还停在旧版，不知道这些目标怎么写（计划书里的 C15 一直没做）。
- **输出格式：已确认用完整世界草稿**（原设计）。曾考虑过的另两种是“参数化”（只选题型和难度参数，世界由代码生成）和“混合”。选择完整草稿的理由：Designer 能发明已有题型之外的新结构，这才是“自我提升”的核心；参数化本质上只是会读失败记录的老虎机。
- **代价**：输出很长、细节多，4B 模型很可能大量写错、通不过认证。认证通过率因此成为第 0 阶段最关键的指标，需要下面这些配套：
  1. **紧凑、有约束的格式**：草稿用最精简的 JSON 结构，生成时用 JSON Schema 约束解码（vLLM 支持），从源头避免格式错误；字段只保留认证必需的部分。
  2. **示例**：提示词里放 2–3 个现有题型（F1、F2、F9 等）生成的真实草稿作参考，降低从零写起的难度。示例要轮换，避免 Designer 只会照抄示例。
  3. **可读的失败原因**：认证不通过时，把具体原因（哪个商品不存在、哪个挑战有歧义、库存不够等）记录下来。第 0 阶段用来统计失败分布、改进提示词；第 2 阶段用来分析 Designer 学到了什么。
  4. **奖励下限**：通不过认证的方案得最低分（见 2.5），让 Designer 在强化学习中先学会写出合格草稿。
  5. **后备方案**：如果第 0 阶段的通过率太低（例如低于 20%），先用现有题型生成的草稿做监督微调，让 Designer 学会格式，再进入强化学习。是否需要，由第 0 阶段的数据决定。
- **改在哪里**：`src/rift/verl/designer.py`（Designer 的生成与解析）、`src/rift/tasks.py`（方案格式）、提示词。

### 2.4 让 Designer 看到训练集失败的隐藏目标

- **改什么**：给 Designer 的失败记录里，除了公开摘要，再加上该任务的结构化目标（哪一行、几件、允许的补救方式）以及哪项判定失败了。**只对训练集开放**；留出集、验证用的题从结构上就不可能进入 Designer 的输入。
- **为什么**：
  - 只看公开过程，有时看不出错在哪。例如 F2 默认题：模型退了 3 件，只看对话会以为退款流程没问题，看到“目标是 1 件”才能诊断出数量错误。
  - 验证用的题与训练失败分开生成（和 X2、X5 的留出集一样用不重叠的种子），开放训练集不会污染验证。
- **改在哪里**：`src/rift/banks/records.py` 的 `FailureObservation`，以及 `src/rift/agents.py` 里交给 Designer 的边界检查（目前明确禁止把任务对象交给 Designer，要改为“仅训练集的结构化目标”）。
- **风险**：Designer 可能直接照抄失败题出“稍改一下”的复制品。对验证没有影响（验证题它从没见过），但可能导致它只出一种题，见 3.1。

### 2.5 Designer 的奖励换成学习信号（计划书 C17）

- **改什么**：Designer 每个方案的奖励 = 它出的题在客服采样中的学习信号（各组 `4p(1−p)` 的平均）。没通过认证的方案得最低分。
- **为什么**：
  - 原设计用双池奖励（恢复减保持损失）。之前的分析：每轮几十个样本时，两个比例之差的噪声约 ±0.08，而一轮训练带来的真实变化只有零点零几，信号会被噪声淹没；而且要等训练后才有奖励。
  - 学习信号在出题的同一轮就有，每个任务组一个数，密得多。老虎机已经证明它能区分“有用题”和“无用题”（无用题 3 轮 对 12 轮）。
- **双池的位置**：不删除，改为验证（第 5 节）和周期性校正。
- **改在哪里**：`src/rift/rewards/learnability.py`（已有计算）、Designer 的训练请求构造。
- **风险**：学习信号奖励“有成有败”，因此有可识别性问题的题、碰运气的题也可能拿高分。2.2 的检查就是为了挡住这一类。

### 2.6 防负迁移：每轮混入其他类的题

- **改什么**：客服每轮训练里，除了 Designer（或老虎机）选的题，**固定混入少量其他类的题**（例如 1/4 的任务从全部题型里均匀抽取）。
- **为什么**：X5 里老虎机大量练“坚持执行退款/换货”的题，F6 拒绝版从 0.16 降到 0.03，8 个任务全部下降，模型在 128 次里有 124 次照样执行换货（原模型是 108 次）。而随机在前两轮练了 F6，就涨到 0.93。只追学习信号会把别的能力练坏，Designer 能无限出同一类题，会比老虎机更严重。
- **改在哪里**：`src/rift/runtime/curriculum_run.py` 的 `train_pool`（每轮组批）。
- **代价**：每轮留给 Designer 的名额少一些。混入比例需要实验确定。

## 3. 第二批：第一批跑通后再改

### 3.1 奖励里加入防重复

- **改什么**：用已有的近似题过滤（`fingerprint.py`），对和近期方案重复的题打折。
- **为什么**：X5 的老虎机 30 轮里 15 轮选了同一类题。Designer 只要找到一类高分题就可能一直出它，造成过度集中和负迁移。

### 3.2 两个模型使用 8 张卡的方式

- **改什么**：先采用“批量”模式：Designer 一次出一批题，客服再训练一段，然后再让 Designer 看新的失败、出下一批。
- **为什么**：两个 4B 模型轮流占用 8 张卡（加载、释放、重新同步）从没在真机上测过（计划书 X10）。每次运行时启动约 5–7 分钟，每轮都切换代价太大。批量模式让前两个阶段几乎不需要切换。
- **之后**：等第 2 阶段训练 Designer 时，再解决两个模型同时驻留或高效切换的问题。

### 3.3 修正老虎机，作为更公平的对比基线

- **改什么**：
  1. 每类题保留最低的被选频率，不要一次低分就放弃（X5 里 F6 只看了一次学习信号 0.08 就被放弃）；
  2. 缩短记忆窗口或让旧记录衰减，题练会后能及时放手（X5 里 F9 延迟版第 21 轮已练会，之后仍被选了 5 次）；
  3. 同时跑“学习进度”策略（代码已有）作对照。
- **为什么**：如果拿有缺陷的老虎机和 Designer 比，Designer 赢了也说明不了太多。

## 4. 不建议现在改的

| 项目 | 原因 |
| --- | --- |
| 订单列表直接显示商品名 | 会改变所有题的难度，所有基线要重测；F1 干扰订单考的“逐个查找”能力也随之消失 |
| 奖励加入过程分 | 你明确不要；坏过程应通过环境后果体现（见第 6 节） |
| 更自然、更多样的请求语言 | 值得做（现在模型靠字符串匹配就能找到商品），但会改变所有题，等 Designer 跑通后再做 |

## 5. 分阶段计划和每阶段的判据

| 阶段 | 做什么 | 回答的问题 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 0：冻结的 Designer 出题 | Designer 不训练，只根据训练集失败出题；只推理 | 方案通过认证的比例及失败原因分布；题的学习信号；是否重复 | 认证通过率足够支撑训练（否则先做格式的监督微调，见 2.3）；通过认证的题学习信号不低于现有题型菜单 |
| 1：用冻结 Designer 的题训练客服 | 预算与 X5 相同，与随机、修正后的老虎机对比；留出集包含 F1 干扰订单 | Designer 出的题能否比固定菜单更有效，尤其能否教会 F1 干扰订单 | 留出集上优于随机和老虎机，且保持类不掉 |
| 2：训练 Designer | Designer 用学习信号做强化学习 | Designer 能否越出越好 | — |

验证方式沿用 X2、X5：训练前后在**同一批没见过的题**上对比，按任务配对重抽样，同时看保持类有没有掉。双池在这里承担“验证”的角色。

## 6. 和环境相关、值得以后做的

只看结果的奖励要能分辨“好过程”和“坏过程”，前提是环境里坏过程有后果：

- **不可撤回的操作**：现在被拒的操作没有任何代价，所以“先乱试再补救”是合理策略（X2 里 F9 学会的正是这个）。
- **会拒绝、会回答问题的客户**：现在客户永远说“好的”，所以“先确认再执行”“信息不足时追问”学不到。

这两项会改变已有题目的难度和基线，建议在 Designer 跑通后单独讨论。

## 7. 环境前提

- `vir-0001`（CANN 8.5）：容器的 1 号进程是 `tail`，不回收子进程，进程表已接近上限（约 40.5 万 / 40.96 万），**在管理员带 init 重建容器之前无法训练**。
- `npu30929`、`npu30001`（CANN 9.1）：没有僵尸问题，但目前被其他人占满。
- 第一批的所有代码改动都可以在本地完成并在 CPU 上演练，不需要等机器。
