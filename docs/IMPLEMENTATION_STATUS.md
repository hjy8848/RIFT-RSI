## Roadmap

This roadmap separates the completed Service hardware smoke from the still-unverified full dual-model RIFT loop.

### Completed: Service training smoke on Ascend

- On 2026-10-30, `npu30001` (8× Ascend 910B3, aarch64) ran VERL 0.9.1 at commit `1876b06d0a3e4e71e06230be10af14492ca8a75b` with the configured Qwen2.5-3B Service model and two GRPO groups of four rollouts each.
- The run used one native Usami smoke task and recorded 8 generations and 8 Episodes. Generation evidence contains actual `generated_token_ids` and `logprobs`.
- VERL restored the initial FSDP2 checkpoint, performed global step 1, saved all eight model/optimizer/state shards, published checkpoint revision 1, and returned a vLLM weight-sync receipt. The before/after weight digests differ.
- All 8 Episodes ended with `service_protocol_error`, and `tool_executions` is empty in every Episode. Five saved generations contain multiple parseable `<tool_call>` blocks in one response; RIFT deliberately rejects more than one call for a native Service decision. The other three contain one parseable call, but their arguments violate the exposed tool schema (`request_policy_review` received nonempty params; `get_case_status` received an unsupported `messages` param). The system prompt already requires exactly one call. The saved token IDs decode into valid Hermes JSON blocks, so the observed failures are model output/turn-boundary failures rather than missing token capture.
- The update receipt reports `service_smoke_completed`; all 8 business rewards were `0.0`, so both four-sample GRPO groups had no reward variation. This verifies real inference, token capture, actor update/checkpoint plumbing, and weight synchronization, but not successful tool execution or reward-driven learning.
- Run artifacts are on the NPU host at `/data/zju-48/hejingyu/rift-runs/smoke-6135942-20261030-r2`; the update receipt is `updates/rift-service-smoke-step-1.json` and the checkpoint transition is recorded in `checkpoints/service-step-1.json`.

## Implemented

- One `BANK_CANDIDATE` task purpose feeds FailureBank and SuccessBank. Bootstrap failures need no ability label; unresolved failures remain recorded. Failure and Recovery no longer form disjoint task partitions.
- AbilityRegistry stores ID, description, explicit failure TaskRefs, training/evaluation history, and explicit link revisions. Designer selects an existing ID or `NEW`; Host validates captured generation, visible IDs and TaskRefs, verifies real Failure Bank evidence, and assigns stable IDs. No semantic matcher or old unused Registry migration branch remains.
- Designer receives opaque `FailureObservation` references with public summaries and available ability choices. Previously shown failures may enter Recovery; task selection must still exclude current Service training overlap and TEST.
- Versioned split registry with unchanged legacy `strict_family_disjoint_v1` behavior and explicit `instance_disjoint_within_family_v1` support.
- Seeded Recovery selection that samples linked failures first and randomly fills from other eligible Failure Bank records, plus independent random Retention sampling. Historical failures must pair with a verified baseline at the current Service checkpoint and protocol. Frozen snapshots persist priority refs, seed, current baseline and same-task/same-seed after-evaluation contracts.
- Dual-bank task-success reward with evidence coverage threshold, before/after checkpoint checks, same training/split isolation checks, and a verifier that reloads and recomputes its evidence.
- Legacy Replay LogP remains a separate tagged reward and state protocol; legacy untagged LoopState loads as Replay LogP.
- Full-parameter VERL role adapters remain in place. Service uses GRPO complete groups. Sequential delayed Designer feedback uses ungrouped REINFORCE with explicit scalar baseline and no batch whitening.
- CommerceHost tries native Grounding candidates in its deterministic, budget-capped order until one certifies. One shared CertifiedTaskRegistry is the task resolver/authorizer for execution; SplitRegistry retains only split-overlap state.
- Default Usami Customer bounds now accept information-only and mixed TaskSpecV3 tasks. The pinned native proof certifier still returns UNKNOWN for information goals until an interaction certifier is supplied; the adapter does not bypass that boundary.
- Malformed Service tool output is recorded by the native Runner as a Service protocol failure. Tool-parser execution exceptions produce a replay-verified cancelled Episode with UNKNOWN business reward and retained token evidence.
- Probe seed is passed to CustomerFactory and seeds each Service generation from a scope stable across before/after checkpoints. Per-generation sampling settings remain in generation evidence.
- Pending Designer generation action is retained and verified through Service training so delayed reward is credited to its exact on-policy rollout.
- A package-level Designer decision now stores one native `ScenarioDraft` plus multiple native `AbstractChallenge` records in the existing exact generation capture. Legacy single-task proposals still load and validate through the same `Proposal`/capture path.
- `CommerceHost.certify_training_plan()` builds one native Usami World, verifies its build, grounds each challenge against that World, tries the bounded deterministic candidate list until certification succeeds, and registers only certified TRAIN tasks. Challenge-level grounding/certification status and reasons remain available to the package assembler.
- `TrainingPackage` freezes the single Designer World, selected ability and original action reference, certified Designer TaskRefs, reproducible samples from a separately frozen certified Usami TRAIN pool, all task source identities, TaskRef-specific GRPO groups, mix settings, seeds, and Service checkpoint. Defaults are one World and 16 tasks split 8+8.
- `prepare_package_service_update()` reuses the native replay-verified capture path and existing `CertifiedTaskRegistry`. GRPO groups cannot mix TaskRefs. UNKNOWN drops a complete group; the realized groups must preserve the configured source ratio or request preparation fails. The package records actual rollout, token and optimization-token counts by source.
- `LoopState` schema 4 records one Designer decision to many training TaskRefs and the realized mixed package. Schemas 1–3 retain the legacy one-proposal/one-task reader. Evolution round planning checks every package identity against both Recovery and Retention snapshots, and the package receives one delayed Designer reward.
- Recovery snapshots exclude the current training package, substantive overlap under the selected split policy, and TEST, but allow previously Designer-visible task references.
- Dual-bank stages are persisted in LoopState. `EvolutionScheduler` and the `rift-evolve` application-factory entry coordinate round execution and checkpoint handoff without embedding fake models or checkpoints.
- `IndependentTestRunner` enforces the TEST purpose boundary; its result is isolated from learning reward and bank updates by the scheduler contract.
- Recovery and Retention after-evaluation now enter `ProbeRunner.after_many()` together. A production evaluator may submit the frozen TaskRef/checkpoint/seed/protocol jobs as one VERL Agent Loop batch; every returned trial is still checked against its original job and evidence verifier. Evaluators without `evaluate_many()` retain the serial path.
- A just-saved FSDP checkpoint now computes model and complete-artifact SHA-256 identities in one content pass. The unchanged-file metadata fingerprint is shared across Checkpoint Store instances in the same worker process, so per-sample Agent Loop construction does not trigger repeated full-file hashing. A persistent runtime can skip disk restore only when `verify_resident_training_state()` attests model, optimizer, scheduler, and RNG state at the requested checkpoint; otherwise the backend restores the full checkpoint and verifies the loaded actor.
- `configs/verl/performance_trial.yaml` is an opt-in FSDP2 Remove-Padding/Dynamic-Batch overlay. It requires `RIFT_PPO_MAX_TOKEN_LEN_PER_GPU` to be selected from measured sequence lengths and device memory, and retains GRPO `rollout.n=4` and generation LogProb capture.
- VERL v0.9.1 already batches Agent Loop samples by creating one task per sample and awaiting them with `asyncio.gather()` in `AgentLoopWorker.generate_sequences()`. RIFT's custom `UsamiServiceAgentLoop.run()` remains the per-sample callback; the application-owned trainer/runtime that supplies batches is not present in this repository, so rollout concurrency is not yet demonstrated end to end. See the pinned [Agent Loop source](https://github.com/verl-project/verl/blob/1876b06d0a3e4e71e06230be10af14492ca8a75b/verl/experimental/agent_loop/agent_loop.py) and [performance guide](https://github.com/verl-project/verl/blob/1876b06d0a3e4e71e06230be10af14492ca8a75b/docs/perf/perf_tuning.rst).
- `rift.runtime` now assembles a production `EvolutionRunRuntime` from validated RIFT/VERL/Ascend config and explicit deployment-owned stores, checkpoint roots, evidence verifiers, and exclusive Service/Designer worker factories. `rift-evolve --deployment-factory module:callable --run-root PATH` validates that binding before starting the existing scheduler; it does not provide fake model workers or default model/data paths.
- The runtime submits Service and Probe requests through the pinned VERL `AgentLoopManager` batch API, validates request identity on return, measures stage timings, persists environment/config snapshots, task certificates, split identities, checkpoint manifests, Probe evidence, and round state, and reconstructs unfinished rounds only from the exact persisted Designer action and frozen plan.
- FSDP2 checkpoint output paths and manifests are unique per role/global step; the scheduler writes a digest-bound finalization marker to avoid repeating a completed round's updates after restart. These recovery boundaries are CPU-tested with doubles; process-crash behavior on a real multi-rank WorkerGroup is unverified.

## Offline verification

On 2026-10-30, the complete CPU suite reported **94 passed** in 125.60 seconds with Python 3.12.7. The targeted production-runtime, VERL bridge, actor mock, and package suites reported **47 passed**. `python -m compileall -q src/rift tests/test_production_runtime.py` and `git diff --check` also passed. The suite exercises unlabelled bootstrap, UNKNOWN exclusion, public failure projection, split policies, explicit `NEW` and existing-ID choices, captured proposal/context binding, cross-round failure reuse, training-overlap exclusion, current-checkpoint baselines, reproducible random fill, TEST rejection, Registry persistence, Probe evidence storage, scripted-evidence rejection from real reward, reward arithmetic, ungrouped Designer credit, dual-bank LoopState save/restore, native information-only Customer execution, multi-candidate certification fallback, seeded probe construction, native parse-failure outcomes, batched Recovery/Retention Probe dispatch, measured-budget Dynamic Batch configuration, resident-state restore gating, production config validation, Agent Loop batch identity checks, exclusive role lifecycle, and checkpoint publication. Package tests additionally certify eight Designer challenges and eight Benchmark tasks through native Usami on CPU, assemble the default 16-task 8+8 package, execute and replay native episodes, verify seeded Benchmark selection and split-overlap rejection, and save/restore package state. Exact model-token capture and production WorkerGroup behavior are exercised with test doubles; these tests do not demonstrate real VERL model learning. Pydantic emitted 17 deprecation/protected-namespace warnings from the current Usami models; they did not fail tests.

## Still required for target deployment

- A deployment-owned `ProductionDeployment` factory that binds the full round to the actual Usami world/task/customer assets, model/tokenizer roots, persistent stores, authoritative identity/split registries, and verified initial checkpoints. The Service smoke used a single generated Usami task and does not provide this full-round binding.
- Real Designer role execution and an explicitly configured Designer checkpoint. The Service role's pinned VERL v0.9.1 FSDP2/vLLM worker group has completed one restore, rollout, update, checkpoint-save, and serving-sync cycle; the Designer path and exclusive two-role lifecycle have not run on hardware.
- A deployment runner that supplies the actual Designer Agent Loop batch and on-policy generation capture while preserving the exact pending action across interruption, plus production update/reward/action/trial verifiers for the complete round.
- Successful reward-driven Service learning after the Hermes boundary fix remains unverified. The latest hardware run completed its real update, but all rewards were zero and six Episodes ended with a Service protocol error.
- Recovery/Retention before-and-after evaluation on independent frozen tasks, current-checkpoint baselines for historical tasks, Replay reward computation, delayed Designer credit, and TEST isolation in a real target-hardware round.
- Target-run selection and profiling of Dynamic Batch token budget, Agent Loop worker count, vLLM concurrency, and NPU memory/throughput. No NPU-specific values are guessed in the overlay.
- The target CustomerFactory must apply the supplied probe seed to its stochastic behavior, and use the same recorded Service sampling protocol before and after updates.
- The deployment must persist real Bootstrap and subsequent task/Probe observations with trusted evidence and use the included plan factory's current-Checkpoint baseline records for historical Recovery and Retention candidates.
- Full-round validation of the exclusive lifecycle for two full-parameter policies sharing the eight NPU devices, including optimizer/RNG restore and safe resource release between Designer and Service phases. Service checkpoint save/restore and serving synchronization are smoke-validated; this does not establish the two-role handoff.
- Full-round validation with the production CustomerFactory, persistent task/Episode stores, Recovery/Retention probes, and TEST isolation. The Service smoke has already exercised the configured parser, real inference server, native Usami execution, and token capture.
- Confirm the supported software image for the complete workload. The pinned VERL v0.9.1 source declares `numpy>=2.0.0`, while the requested image specifies NumPy 1.26.4. The Service smoke ran in the configured environment, but the full dependency set has not been validated; no dependency override is claimed safe.

The initial 2026-10-30 Ascend Service smoke and the later Hermes-boundary rerun both completed one FSDP2 update, but the latest run's eight business rewards were all `0.0`; there is no evidence of reward-driven capability gain. The Hermes evidence fix and vLLM CANN `PYTHONPATH` forwarding are hardware-smoke validated. No full-round Replay reward, Designer update, forgetting measurement, or independent TEST evaluation has run on the target hardware. Probe batching and resident-state restore remain supported by offline interface tests only. The smoke's total wall time remains around 18 minutes, and vLLM child cleanup after driver exit needs a supported shutdown path.
