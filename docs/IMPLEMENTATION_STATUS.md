This document records which pieces of the dual-bank RIFT protocol have code and offline tests. The research objective is defined in [RESEARCH_SPEC.md](RESEARCH_SPEC.md); executable contracts are in `src/rift/` and defaults in `configs/dual_bank.yaml`.

## Implemented

- One `BANK_CANDIDATE` task purpose feeds FailureBank and SuccessBank. Bootstrap failures need no ability label; unresolved failures remain recorded. Failure and Recovery no longer form disjoint task partitions.
- AbilityRegistry stores ID, description, explicit failure TaskRefs, training/evaluation history, and explicit link revisions. Designer selects an existing ID or `NEW`; Host validates captured generation, visible IDs and TaskRefs, verifies real Failure Bank evidence, and assigns stable IDs. No semantic matcher or old unused Registry migration branch remains.
- Designer receives opaque `FailureObservation` references with public summaries and available ability choices. Previously shown failures may enter Recovery; task selection must still exclude current Service training overlap and TEST.
- Versioned split registry with unchanged legacy `strict_family_disjoint_v1` behavior and explicit `instance_disjoint_within_family_v1` support.
- Seeded Recovery selection that samples linked failures first and randomly fills from other eligible Failure Bank records, plus independent random Retention sampling. Historical failures must pair with a verified baseline at the current Service checkpoint and protocol. Frozen snapshots persist priority refs, seed, current baseline and same-task/same-seed after-evaluation contracts.
- Dual-bank task-success reward with evidence coverage threshold, before/after checkpoint checks, same training/split isolation checks, and a verifier that reloads and recomputes its evidence.
- Legacy Replay LogP remains a separate tagged reward and state protocol; legacy untagged LoopState loads as Replay LogP.
- Full-parameter VERL role adapters remain in place. Service uses GRPO complete groups. Sequential delayed Designer feedback uses ungrouped REINFORCE with explicit scalar baseline and no batch whitening.
- CommerceHost tries native Grounding candidates in its deterministic, budget-capped order until one certifies. One shared CertifiedTaskRegistry is the task resolver/authorizer for execution; SplitRegistry retains only split-overlap state.
- Default Usami Customer bounds now accept information-only and mixed TaskSpecV3 tasks. The pinned native proof certifier still returns UNKNOWN for information goals until an interaction certifier is supplied; the adapter does not bypass that boundary.
- Malformed Service tool output is recorded by the native Runner as a Service protocol failure. Tool-parser execution exceptions produce a replay-verified cancelled Episode with UNKNOWN business reward and retained token evidence.
- Probe seed is passed to CustomerFactory and seeds each Service generation from a scope stable across before/after checkpoints. Per-generation sampling settings remain in generation evidence.
- Pending Designer generation action is retained and verified through Service training so delayed reward is credited to its exact on-policy rollout.
- A package-level Designer decision now stores one native `ScenarioDraft` plus multiple native `AbstractChallenge` records in the existing exact generation capture. Legacy single-task proposals still load and validate through the same `Proposal`/capture path.
- `CommerceHost.certify_training_plan()` builds one native Usami World, verifies its build, grounds each challenge against that World, tries the bounded deterministic candidate list until certification succeeds, and registers only certified TRAIN tasks. Challenge-level grounding/certification status and reasons remain available to the package assembler.
- `TrainingPackage` freezes the single Designer World, selected ability and original action reference, certified Designer TaskRefs, reproducible samples from a separately frozen certified Usami TRAIN pool, all task source identities, TaskRef-specific GRPO groups, mix settings, seeds, and Service checkpoint. Defaults are one World and 16 tasks split 8+8.
- `prepare_package_service_update()` reuses the native replay-verified capture path and existing `CertifiedTaskRegistry`. GRPO groups cannot mix TaskRefs. UNKNOWN drops a complete group; the realized groups must preserve the configured source ratio or request preparation fails. The package records actual rollout, token and optimization-token counts by source.
- `LoopState` schema 4 records one Designer decision to many training TaskRefs and the realized mixed package. Schemas 1–3 retain the legacy one-proposal/one-task reader. Evolution round planning checks every package identity against both Recovery and Retention snapshots, and the package receives one delayed Designer reward.
- Recovery snapshots exclude the current training package, substantive overlap under the selected split policy, and TEST, but allow previously Designer-visible task references.
- Dual-bank stages are persisted in LoopState. `EvolutionScheduler` and the `rift-evolve` application-factory entry coordinate round execution and checkpoint handoff without embedding fake models or checkpoints.
- `IndependentTestRunner` enforces the TEST purpose boundary; its result is isolated from learning reward and bank updates by the scheduler contract.
- Recovery and Retention after-evaluation now enter `ProbeRunner.after_many()` together. A production evaluator may submit the frozen TaskRef/checkpoint/seed/protocol jobs as one VERL Agent Loop batch; every returned trial is still checked against its original job and evidence verifier. Evaluators without `evaluate_many()` retain the serial path.
- A just-saved FSDP checkpoint now computes model and complete-artifact SHA-256 identities in one content pass. The unchanged-file metadata fingerprint is shared across Checkpoint Store instances in the same worker process, so per-sample Agent Loop construction does not trigger repeated full-file hashing. A persistent runtime can skip disk restore only when `verify_resident_training_state()` attests model, optimizer, scheduler, and RNG state at the requested checkpoint; otherwise the backend restores the full checkpoint and verifies the loaded actor.
- `configs/verl/performance_trial.yaml` is an opt-in FSDP2 Remove-Padding/Dynamic-Batch overlay. It requires `RIFT_PPO_MAX_TOKEN_LEN_PER_GPU` to be selected from measured sequence lengths and device memory, and retains GRPO `rollout.n=4` and generation LogProb capture.
- VERL v0.9.1 already batches Agent Loop samples by creating one task per sample and awaiting them with `asyncio.gather()` in `AgentLoopWorker.generate_sequences()`. RIFT's custom `UsamiServiceAgentLoop.run()` remains the per-sample callback; the application-owned trainer/runtime that supplies batches is not present in this repository, so rollout concurrency is not yet demonstrated end to end. See the pinned [Agent Loop source](https://github.com/verl-project/verl/blob/1876b06d0a3e4e71e06230be10af14492ca8a75b/verl/experimental/agent_loop/agent_loop.py) and [performance guide](https://github.com/verl-project/verl/blob/1876b06d0a3e4e71e06230be10af14492ca8a75b/docs/perf/perf_tuning.rst).

## Offline verification

On 2026-10-29, the complete CPU suite reported **83 passed**. It exercises unlabelled bootstrap, UNKNOWN exclusion, public failure projection, split policies, explicit `NEW` and existing-ID choices, captured proposal/context binding, cross-round failure reuse, training-overlap exclusion, current-checkpoint baselines, reproducible random fill, TEST rejection, Registry persistence, Probe evidence storage, scripted-evidence rejection from real reward, reward arithmetic, ungrouped Designer credit, dual-bank LoopState save/restore, native information-only Customer execution, multi-candidate certification fallback, seeded probe construction, native parse-failure outcomes, batched Recovery/Retention Probe dispatch, measured-budget Dynamic Batch configuration, resident-state restore gating, and single-pass checkpoint publication. The package tests additionally certify eight Designer challenges and eight Benchmark tasks through native Usami on CPU, assemble the default 16-task 8+8 package, execute and replay native episodes, verify seeded Benchmark selection and split-overlap rejection, and save/restore package state. The Service package capture adapter and exact model-token capture are exercised with explicit test doubles; neither that path nor the rest of the test suite demonstrates real VERL model learning.

## Still required from a deployment runtime

- A production `EvolutionRunRuntime` factory with persistent Usami task/certificate/Episode stores, authoritative identity construction, native multi-turn evaluator, real VERL FSDP2 worker groups, checkpoint store, and production update/reward/action/trial verifiers.
- A production batched Probe evaluator that submits `evaluate_many()` requests to the standard VERL Agent Loop worker, and a runtime factory that feeds Service GRPO groups through VERL's built-in batch path. The repository currently has the batching contract and coordinator wiring, but no production evaluator/runtime implementation.
- Target-run selection and profiling of Dynamic Batch token budget, Agent Loop worker count, vLLM concurrency, and NPU memory/throughput. No NPU-specific values are guessed in the overlay.
- A production CustomerFactory that applies the supplied probe seed to its stochastic behavior, and an evaluator that uses the same recorded Service sampling protocol before and after updates.
- A bank updater that persists real Bootstrap and subsequent task/probe observations with trusted evidence, and a plan factory that restores the exact pending Designer action on interrupted rounds and supplies current-Checkpoint baseline records for historical Recovery and Retention candidates.
- A tested exclusive lifecycle for two full-parameter policies sharing the eight NPU devices, including optimizer/RNG restore, serving weight synchronization, and safe resource release between Designer and Service phases.
- Integration validation with the configured VERL parser, real inference server, production CustomerFactory, persistent task/Episode stores, and Agent Loop token capture.
- Resolution and validation of the requested software image. The pinned VERL v0.9.1 source requires `numpy>=2.0.0`, which conflicts with requested NumPy 1.26.4; no dependency override is claimed safe.

No real training, model inference, checkpoint update, replay measurement, capability acquisition, forgetting measurement, or Ascend job has been run. Probe batching and resident-state restore have only offline interface tests; speedup is not established. A real experiment remains unverified until performed in the target environment using `configs/dual_bank.yaml` and independently frozen TEST tasks.
