## 0. 一页摘要

**问题。** 现在 Designer 的训练信号是"双池奖励"：Service 更新一步后，在独立探针上算成功率的变化。这个信号又贵又吵：

- 每轮只有一个标量，要给一长串出题决定记功；
- 一半训练题是基准题，和 Designer 无关，却混进同一个奖励；
- 噪声标准差约 0.05–0.07（玩具模拟，未实测），而一步小更新的真实提升可能只有 0.02；
- Recovery 探针优先抽 Designer 刚看过的失败任务，奖励可以靠"出近似复制品"刷高。

**策略。**

1. 把双池奖励从"逐轮训练信号"降级成"偶尔做的验证"，验证用**配对对照**（同一起点，一份用 Designer 的包训练，一份用对照包训练）。
2. 训练 Designer / 课程用 Service 本来就在算的**密集代理信号**：Designer 自己出的每道题，GRPO 的 4 次采样是否"有好有坏"。
3. 补上让这个代理可信的配套：任务歧义检查、近似题过滤、"应当拒绝"类任务、可控的合成任务族库。
4. 先做一个**结构化课程基线**（随机 / 仅难度 / 学习进度 / 老虎机），LLM Designer 必须赢过它才值得继续。

**已完成**（不在本计划范围内）：Phase 3 业务能力；VERL 桥接测试修复（全量 204 通过）；Probe 基线偏差修复（零更新时假提升 +0.111 降到 −0.016，见 `DUAL_BANK_DESIGN.md`）。

**已确认的决定**（D1–D6）见第 5 节。尚未确认的只有各实验的通过/失败阈值，实验开跑前必须定下。

### C1　学习价值代理 `learnability_v1`　【P0 · S】

- **目标**：把 GRPO 分组结果变成每道题的"可学性"，作为课程/Designer 的密集信号。
- **位置**：新建 `src/rift/rewards/learnability.py`。纯函数加验证器，不改任何旧结构。
- **输入**：`TrainingPackage.task_groups`（`task_ref`、`group_id`、`group_size`、`source`）和 `UpdateRequest.rollouts`（`task_id`、`group_id`、`reward ∈ {0,1}`）。被 UNKNOWN 整组丢弃的任务不在 rollouts 里。
- **定义**：对每个完整组，k 为成功数，G 为组大小，p̂ = k/G，**ℓ = 4·p̂·(1−p̂)**（G=4 时取值 0 / 0.75 / 1）；"有信息" ⇔ 0 < k < G。
- **输出** `LearnabilityStats`：每任务 `(task_ref, source, k, G, ℓ)`；`designer_mean`、`benchmark_mean`、`designer_informative_fraction`、`designer_valid_groups / expected_groups`。
- **标量**：`designer_mean`。`benchmark_mean` 只用于诊断（Service 整体是否卡住），**不进入奖励**。
- **证据下限**：Designer 来源的有效组占预期组的比例低于 `min_valid`（默认 0.5）时，沿用 `InsufficientEvidenceError`，不给标量。
- **验证器**：从可信的 `UpdateRequest` 重算并比对，沿用 `reward_verifier` 的模式。
- **验收测试**：k=0..4 的公式值；UNKNOWN 组缺失时的分母；覆盖率不足拒绝；篡改计数被验证器发现；来源划分正确；基准均值不影响标量。
- **注意**：ℓ 在 p̂=0.5 最大。歧义题会把 ℓ 撑高，所以必须配 C4。

### C2　任务族库与难度旋钮　【P0 · L】

- **目标**：给项目一个**可控、可复现、知道真实结构**的任务分布，同时充当基准池、课程的臂、和"兄弟实例"的来源。
- **位置**：新建 `src/rift/benchmark/families.py`。使用 `ScenarioDraft` 与 `AbstractChallenge`。
- **接口**：`Family.build(knobs, seed) → (ScenarioDraft, challenges)`。产出直接是现有 `Proposal(world_draft, challenges)`，因此 `CommerceHost.certify_training_plan` 不用改。
- **可重建性**：每个实例在 `Identity.family`、`lineage` 里记 `family_id`、旋钮、`spec_hash`、`challenge_hash`、`world_seed`；提供 `sibling(instance, new_seed)` 生成同能力、不同实例的兄弟题。
- **初始族**：

| 族 | 测什么 | 主要旋钮 |
| --- | --- | --- |
| F1 退款-基础 | 基本工具使用 | 干扰订单数 |
| F2 退款-部分数量 | 数量识别 | 购买数量、退几件 |
| F3 退款-贴近审批上限 | 金额边界（可办 / 不可办） | 金额相对上限的比例 |
| F4 退款-退货窗口边界 | 时间边界 | 距送达天数相对窗口 |
| F5 取消 | 状态判断 | 订单是否已发货 |
| F6 换货-差价 | 价格推理 | 差价相对客户上限 |
| F7 换货-库存回退 | 库存与时效 | 最快仓库库存、到货期限 |
| F8 补发 | 资格与库存 | 库存、送达问题记录 |
| F9 实物退货 | 外部事件 | 收货延迟天数 |
| F10 多行挑选 | 识别目标行 | 干扰行数 |
| F11 多目标组合 | 多目标规划 | 目标数、订单数 |

  F3、F4、F5、F6、F8 各配**拒绝变体**（见 C3）。
- **要求**：每个（族，旋钮档）在 N 个种子下都 SAT、可 grounding、可认证（或可出拒绝证书），并通过 C4。
- **标注**：`DistributionSpec` 里的来源标为 `synthetic_assumption`，文档不得声称代表真实分布。
- **验收测试**：确定性（同种子同结果）；所有 Engine/Reference/Oracle/Replay 路径通过；兄弟题与原题"能力相同、实例不同"。
- **依赖**：C3（拒绝变体）、C4（可识别性）。

### C3　拒绝目标 `RefusalGoal` 与拒绝证书　【P0 · M】

- **目标**：让"正确答案是不执行"的任务进入训练，打破"总是去办"的最优策略。
- **目标类**：`scenarios/tasks.py` 新增 `RefusalGoal(goal_id, line_ids, reason_code)`；`TaskSpecV3.refusal_goals` 默认空、省略序列化（照 `cancellation_goals`）。
- **委托**：拒绝行**要**纳入 `delegated_line_ids`。客户确实提了请求，Service 若强行操作，应当被**业务规则**拒绝，而不是被"缺委托"拒绝。
- **求值**（只看状态与工具轨迹，不涉及自然语言）：PASS 当且仅当
  1. 这些行没有新增结算、账务、履约；
  2. Service 对每个相关订单成功调用过至少一次 `get_order_details`；
  3. Episode 以 `customer_finished` 结束。
- **认证**：新建独立的 `certify_refusal(...)`，返回新的 `RefusalCertificate`，**不改 `TaskCertification`**。流程：对被拒动作在 Engine + Reference + Oracle 下执行；要求被拒、错误码等于目标声明的 `reason_code`、Oracle 通过、候选集穷尽且无 blocker。`CertifiedTaskRegistry._check` 同时接受两类证书。
- **Designer 侧**：`RefusalDraft`；grounding 选择器已有 `fulfillment_status`、年龄上下界，够用。
- **验收测试**：每个 `reason_code`（`RETURN_WINDOW_EXPIRED`、`ORDER_NOT_CANCELLABLE`、`APPROVAL_REQUIRED`、`INSUFFICIENT_STOCK`、`ORDER_NOT_DELIVERED`）；Service 什么都不做 → 未读详情则 FAIL；乱办被规则拒绝但状态不变 → PASS；办成了别的行 → 未请求结算 FAIL。
- **待你拍板**：条件 2（必须读过详情）是否接受，见 D3。
- **风险**：这是最需要小心的一项，证书与注册表耦合；所以先做独立证书类。

### C4　请求可识别性检查　【P0 · S】

- **问题（已核实）**：旧 v2 任务检查"请求文字能唯一定位到目标行"（`public_line_match_ids`），v3 没有。两行描述相同时，Service 只能蒙，成功率被随机性撑到约 50%，C1 的代理会奖励这种题。
- **做法**：编译期检查。目标行的公开描述（`_line_description`）在同客户的所有行里必须唯一；取消目标按"商品描述集合"判断唯一。不唯一就抛 `TaskCapabilityUnsupported`，代码 `AMBIGUOUS_TARGET`。
- **位置**：`designer.compile_task`，以及 C2 的族构造。**不要**放进 `check_task_scope` 或 `certify_task`，否则历史任务回放会失败。
- **验收测试**：两行同描述 → 拒绝；属性不同 → 通过；取消、换货、拒绝目标都覆盖。

### C5　近似题指纹过滤　【P1 · M】

- **目标**：堵住"出近似复制品教探针"。
- **指纹**：`src/rift/probes/fingerprint.py`，`task_fingerprint(world, task)` 由结构化目标算出：补救类型集合、商品族、属性值、数量档、订单状态、金额档、年龄档、是否需退回、目标数。
- **规则**：`ProbeSelector.preselect/freeze` 增加 `fingerprint_resolver`、`min_distance`；与任何训练任务指纹距离小于阈值的探针候选被排除，原因码 `near_duplicate_of_training`。默认关闭（兼容旧调用）。
- **边界**：同能力、不同实例**要**保留（那是 instance-disjoint 政策本来允许的）；只排除"所有离散字段相同且数值档位相邻"的近似题。
- **阈值**：不要拍脑袋，由 X6 校准。
- **验收测试**：仅 ID 不同的两题 → 排除；补救类型不同 → 保留；数量档差一档但其他全同 → 排除（可配置）。

### C6　课程运行器与结构化课程策略　【P0 · L】

- **目标**：用比 LoopState 轻得多的循环做阶段 2 的科学对比，LLM Designer 之后再接入。
- **位置**：新建 `src/rift/evolution/curriculum.py`。
- **策略接口**：`propose(round_index, history) → Selection(family_id, knobs, n_tasks)`；`observe(selection, LearnabilityStats)`。
- **策略实现**：
  - `RandomPolicy`：在臂上均匀随机；
  - `FixedFamilyPolicy`：固定一个族（给 X4 用）；
  - `DifficultyOnlyPolicy`：选历史通过率最接近 0.5 的臂；
  - `LearningProgressPolicy`：选 ℓ 的滑动变化最大的臂；
  - `BanditPolicy`：对每个臂的 ℓ 做 Thompson 采样（高斯后验或 Beta 伪计数）。
- **运行一轮**：`policy.propose` → 族库生成 `Proposal` → `CommerceHost.certify_training_plan`（复用）→ 与基准任务混成 `TrainingPackage`（复用 `assemble_training_package`）→ `ProductionServiceRolloutCollector` → `service_backend.train` → C1 算 `LearnabilityStats` → `policy.observe` → 每 K 轮做验证（C7）。
- **持久化**：逐轮 JSONL 加每轮检查点目录，支持断点续跑，**不进 LoopState**。
- **证据**：全部沿用现有验证器与回放。
- **预算对齐**：所有策略在相同轮数、相同 rollout 数、相同种子集下比较。
- **验收测试**：在合成环境里（已知各臂的真实 ℓ），Bandit 能找到最优臂；各策略可复现；预算对齐；断点续跑一致。

### C7　配对对照验证　【P1 · M】

- **目标**：在同一起点上比较"课程包"与"对照包"，抵消共同噪声。
- **位置**：新建 `src/rift/evolution/matched_control.py`，做成独立脚本入口，**不嵌进调度器**。
- **流程**：固定 θ 与一对冻结探针（含独立基线，见已完成的修复）→ 臂 A 用课程包更新、臂 B 用对照包更新（基准专用或随机族包），二者 rollout 数、优化步数、超参相同 → 两臂各自评估**同一组**冻结探针 → 输出两臂的 G、H、R 和配对差值。
- **关键点**：第二臂必须从 θ 重新恢复。现有 `verify_resident_training_state` 会因 `_loaded_checkpoint != policy_before` 自动触发从磁盘恢复，但要加测试确认。两臂的训练身份都要与探针不重叠，`score_dual_bank` 才会放行。
- **验收测试**：用假后端验证配对结构、探针摘要共用、检查点恢复；差值计算正确。

### C8　更新幅度与学习率可配置　【P0 · S】

- **问题（已核实）**：`create_update_backend` 里 `mini_batch_size=max(WORLD_SIZE, len(request.rollouts))`、`epochs=1`，即每轮恰好 1 个优化步；`_verl_config` 里学习率写死 1e-6。
- **做法**：`configs/dual_bank.yaml` 增加
  ```yaml
  service:
    update: {mini_batch_size: 64, epochs: 1, learning_rate: 1.0e-6}
  ```
  默认保持现有行为。`ascend_910b3._verl_config(..., learning_rate)`、`create_update_backend(mini_batch_size, epochs)` 参数化；`ProductionConfig.validate` 校验整除（`train()` 里已有同样的运行时检查）。
- **要核对（我没读）**：`total_training_steps=1` 与 VERL 学习率调度器、warmup 的交互；多步更新后 `global_step` 仍按外层批次加 1 的假设。
- **不要做**：学习率设为 0。`training/contracts.py:73` 与 `verl/update_ledger.py:24` 都要求前后权重摘要不同；bf16 下极小学习率可能一个权重都不变，同样被拒。零更新对照改用 X0 的做法。

### C9　基准池通过率带与任务统计存储　【P1 · M】

- **目标**：训练题尽量落在"有信息"的区间，避免整批白跑。
- **`TaskStatsStore`**：追加式 JSON，记 `(task_ref, checkpoint, round, successes, group_size)`；数据来自每轮 Service 分组结果，**不额外花 rollout**。
- **打包**：`assemble_training_package` 增加资格函数：优先最近一次观测通过率在 [0.2, 0.8] 内的基准任务；没有观测的任务按"探索"处理；定期重新标定，因为 Service 变强后通过率会漂移。

### C10　丢弃零方差组　【P2 · M】

### X0　测量噪声与确定性（先做，最便宜）

- **为什么不用 lr=0**：会被 `contracts.py:73` / `update_ledger.py:24` 拒绝（见 C8）。噪声底改用"不训练、重复测量"来量。
- **X0-A 噪声**：固定 θ₀，选 16 个 Recovery 候选和 16 个 Retention 候选（来自 C2 的中等难度族）。对同一 θ₀ 做 M=20 次独立测量，每次用全新种子集（每任务 5 次），对每次测两遍得到 A、B，差值 D = mean(A) − mean(B)。这正是"零更新时奖励的分布"。
- **X0-A' 确定性**：同权重、同种子、同任务重复运行 → 记录"逐 token 完全一致比例"和"逐 Episode 结果一致比例"。这直接测出我模拟里的未知参数 r（重放一致率）。
- **指标**：SD(D)，并与理论值 √(2p(1−p)/N)（N=80 时约 0.079）对比；r；vLLM 在批处理下是否 batch-invariant。
- **判据（建议）**：
  - r ≥ 0.95 → 共享种子的配对设计有效，噪声主要来自更新引起的分歧；
  - r < 0.5 → 配对无用，探针只能靠增大 N 或跨任务聚合；
  - SD(D) 明显大于理论值 → 存在额外方差源（客户模拟随机性、批处理数值差异）。
- **失败分支**：若 SD(D) > 0.06 且 r 低，双池奖励只用于大样本聚合验证（C7），不再逐轮使用。
- **规模**：32 任务 × 5 次 × 2 遍 × 20 次 = 6400，另加确定性测试约 300。只推理，不训练。

### X0-B　极小更新灵敏度（可选）

- 以 lr ∈ {1e-7, 3e-7, 1e-6} 各做一次真实更新（摘要必须不同），测同一探针更新后的轨迹分歧率与 G。
- 目的：画出"重放一致率 r 随更新幅度的变化曲线"，并确认保存、恢复、同步在小更新下正常。
- 若 1e-7 已被拒（权重未变），记录下来，这本身就是 bf16 下的最小可检测更新。

### X1　起点标定与协议错误诊断

- **做法**：对 C2 的每个族取 3 档旋钮、每档 8 个实例、每个实例 16 次 rollout，只推理。记录通过率（含置信区间）、协议错误率及类型（C12）、工具调用直方图、响应长度。
- **回答**：
  1. 哪些族的起点通过率落在 [0.2, 0.8]，可直接做训练带（给 C9 用）；
  2. 上次的协议错误是模型输出问题，还是适配层（解析器、schema、提示）问题；
  3. 起点是否接近 0。
- **判据（建议）**：若最简单的 3 个族的平均通过率低于 0.05 → 先做示范起步（D4），否则 X2 之后的一切都没有梯度。若协议错误占失败的一半以上 → 先修协议问题，再谈课程。
- **规模**：约 12 族 × 3 档 × 8 实例 × 16 ≈ 4600。

### X2　Service 单独学习曲线与更新幅度扫描

- **做法**：选 2–3 个中等通过率的族，只训练 Service，30–50 轮；扫描 (mini_batch_size, 学习率) 的几个组合（如 64/1e-6、16/1e-6、16/2e-6）。每个设置至少 2 个种子。
- **指标**：训练通过率曲线；在**兄弟实例**上的留出通过率；有信息组占比；响应长度；熵或 KL（若可取）；在未训练的族上的通过率（遗忘检查）。
- **判据（建议）**：最佳设置下，兄弟实例留出通过率在预算内提升不少于 +0.10（绝对值）。
- **失败分支**：不涨 → 问题在模型、格式或工具，不是课程，转向示范起步（D4）或简化工具；涨但遗忘严重 → 降低更新幅度。

### X3　工具面 A/B

- **做法**：同一批退款类任务（`core4` 能表达的），分别用 `core4` 与 `full9`，各 ≥3 个种子，比较协议错误率和通过率；再在 `full9` 下加上取消、换货等任务的结果作为参考。
- **判据（建议）**：若 `full9` 的协议错误率比 `core4` 高 10 个百分点以上，或通过率低 0.05 以上 → 回到按任务类型暴露相关工具子集，或分阶段引入新工具。

### X4　代理奖励有效性（最关键的一项）

- **思路**：族是人工设计的，真实收益排序可以实测。用它检验"早期代理信号能不能预测真实收益"，**不涉及 Designer**。
- **做法**：选 K=4–6 个族（含 1–2 个有意设计的"歧义陷阱"族，关闭 C4 的过滤）。对每个族分别训练 Service 同样预算（如 20 轮）、每族 ≥3 个种子；训练前后用**同一组冻结探针**（含兄弟实例）测 Recovery/Retention；同时记录前几轮的 ℓ̄。
- **指标**：
  1. 各族真实收益 G_k 的跨种子一致性（族排序的 Kendall τ）；
  2. 早期 ℓ̄_k（前 5 轮）与 G_k 的 Spearman 相关；
  3. 陷阱族上 ℓ̄ 是否虚高、而 G 是否不涨。
- **判据（建议）**：族排序跨种子 τ ≥ 0.5，且 ℓ̄ 与 G 的 Spearman ≥ 0.6 → 代理可用；陷阱族被 C4 过滤后不再虚高。
- **失败分支**：族排序本身不稳定 → 说明在当前预算下探针对"哪类题更好"没有分辨力，要先增大 N 或更新幅度（回 X0、X2）。代理与收益相关性低 → 重新设计代理（例如改用优势绝对值、或要求成功轨迹一致）。
- **规模**：6 族 × 3 种子 ×（20 轮 × 64 训练 + 前后探针各约 320）≈ 30k；缩减版 4 族 × 2 种子约 10k。

### X5　课程策略对比

- **做法**：Random / DifficultyOnly / LearningProgress / Bandit 四种策略，相同轮数（建议 30–50）、相同 rollout 预算、≥3 个种子；每 K=5 轮做一次 C7 配对验证；最终在共享探针（含兄弟实例）上比较。
- **指标**：最终 Recovery 提升、Retention 变化、兄弟实例泛化、各臂被选次数分布。
- **判据（建议）**：Bandit 相对 Random 的最终提升 ≥ +0.05，且 95% 置信区间不含 0 → 成功。
- **解读**：配对验证只能检出约 0.05 以上的差异，更小的真实效应检不出来，不能据此说"没有效果"。
- **失败分支**：Bandit 不优于 Random → 代理不可靠或课程价值本身很小；如实报告负结果，回到 X4 查代理。

### X6　近似题阈值校准与教探针审计

- **做法**：由真实失败任务生成三类训练题：(a) 近似复制品（只改 ID 或数值微调），(b) 兄弟实例（同能力、不同实例），(c) 同能力的不同难度。各训练一轮，比较 Recovery 原探针与兄弟探针上的提升。
- **指标**：(a) 在原探针上的提升显著高于在兄弟探针上 → 证实"可以教探针"；校准 C5 的指纹距离阈值，使 (a) 被过滤而 (b)(c) 不被过滤。
- **用途**：给 C5 一个有依据的默认阈值；给 X7 提供审计标准。

### X7　LLM Designer 与代理奖励

- **前提**：X5 通过；C15、C17 完成。
- **做法**：LLM Designer 用 C1 的代理奖励（滑动均值基线）训练；与 X5 的 Bandit、Random 在相同预算下对比；每 K 轮做配对验证。
- **审计**：Designer 产出的任务里，近似复制品比例（C5 指纹）、歧义题比例（C4）、有信息比例、族多样性（熵）是否塌缩。
- **判据（建议）**：LLM Designer 相对 Bandit 的最终提升 ≥ +0.03 且置信区间不含 0。
- **失败分支**：不如 Bandit → 在当前预算下，用 RL 训 Designer 不值得，把结论写成负结果或把 Designer 降级为"在族库里提出新旋钮组合"。

### X8　拒绝与确认类任务的训练效应

- **做法**：在训练混合里加入拒绝变体和拒绝的客户；用"总是去办"和"总是不办"两个退化策略作参照；比较执行类任务通过率与拒绝类任务通过率的权衡。若 D2 启用顺序合规，同时统计"先问再办"的比例。
- **判据（建议）**：训练后拒绝类通过率明显高于"总是去办"基线，且执行类通过率下降不超过 0.05。

## 附录 A　关键数字与公式

- 两比例之差的标准差（各 N 次试验，p=0.5）：√(2·p(1−p)/N)。N=80 → 0.079；N=320 → 0.040；N=1250 → 0.020。
- 一组 4 次采样"有好有坏"的概率 = 1 − p⁴ − (1−p)⁴：p=0.5 → 87.5%；0.1 → 34%；0.05 → 19%；0.02 → 8%。
- 两样本检验所需每组样本数 ≈ 2·(1.96+0.84)²·σ²/Δ² ≈ 15.7·σ²/Δ²。σ=0.06、Δ=0.02 → 约 141 轮。
- 零更新时的虚假提升（真实管线，60 轮）：旧做法 +0.111；修复后 −0.016（标准误 0.012）。
- 5 次试验的分类噪声：真实通过率 0.5 的任务，被误判为"弱点"（≤1/5 成功）的概率为 (1+5)/32 ≈ 18.8%，被误判为"已掌握"（≥4/5 成功）同样约 18.8%。
